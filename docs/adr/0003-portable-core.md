# The backend core stays portable: pure functions on JSON data, typed errors, golden cases

We plan to keep the application in Python for now and may move the backend to Rust later. To make that move cheap we fixed a boundary instead of restructuring: logic in a pure "core" zone takes and returns JSON-like data, does no I/O, reads no environment, clock or randomness, calls no Pydantic behaviour, and fails with `kitchen.errors` types. I/O, configuration and persistence live in a "shell" zone, and numpy/PIL image work in a "pixel" zone that is compared by tolerance, not bit for bit. The rules (R1-R24, in `CODING_STANDARDS.md`; R24 is from `0004-business-data-in-the-catalog.md`) are enforced by `tests/test_architecture.py`; behaviour is pinned by JSON golden cases in `tests/golden/` that a Rust build can run unchanged. Existing violations are listed in `tests/architecture_allowlist.py`, which may only shrink.

Rejected: moving to a `core/` package or imitating Rust types in Python now (churn without behaviour pinned), forbidding `extra="allow"` on the spec models (it would break the stored designs and older files), and requiring bit-identical images (the Rust image libraries differ). Known traps this decision records: Python's `round` rounds halves to even while Rust's `f64::round` rounds away from zero (`numeric.round_half_away` is the single rounding), `dict` keeps insertion order but a Rust `HashMap` does not, and canonical JSON for `op_hash` must match Python's `json.dumps(sort_keys=True, separators=(",", ":"), ensure_ascii=False)` including float formatting.
